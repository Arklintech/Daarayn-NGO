# D32 Data onboarding preparation report

Real data onboarding is a SEPARATE future stage. In D31 and D32 no real donor data was requested, no dummy record was migrated, no production worksheet was created or changed, no communication was sent. This report prepares the plan and the tooling only. The records currently in the TEST spreadsheet are engineering test data and must never be copied to production.

## 1. Schema-only worksheet plan (source: `docs/migration/PRODUCTION_SCHEMA_PREPARATION.md` and the repository registry)
Missing in production and required before any financial activation: `Allocations`, `Donation_Causes`, `Communication_Recipients`, `Program_Content` (blocking); `Portal_Auth_Events`, `_Secrets` (features). The exact header rows are listed in that document; they come from the repositories' registered schemas, so creating them is done by the application's own idempotent setup (`ensureSheetExists` with the registered headers) and NOT by hand, which keeps column order and names identical to the code. Present-but-legacy worksheets (`Causes`, `Donors`, `Donations`, `Field_Reports`, `Communications`) get missing columns appended on first write (supported fallback); duplicate, empty or renamed headers block and are reported by the drift checker. Creation of empty production structures needs the owner's explicit authorisation, a fresh copy of the spreadsheet as backup and the write guard set to production for that single operation; no dummy rows are written.

## 2. Permanent identifier strategy (verified from the code)
Donor token `DNR-<base36 time>-<4 random>`, donation id `DA<number>` assigned by the application with a claim marker, allocation ids generated by the service, designations `DC-<donation>-<cause>`; the submission key and request key give idempotency. Imported records must keep their original permanent ids; the validator below rejects duplicates and malformed ids; the application's own counters must be set above the highest imported donation number BEFORE live donations resume (to be verified in the rehearsal).

## 3. Validation tooling (IMPLEMENTED, TESTED LOCALLY)
`lib/onboarding/validate.ts` (pure, no Google request) checks a batch for: missing, malformed and duplicate permanent ids; donations that refer to missing donors; designations that refer to missing donations or causes and duplicate designations; allocations without a designation; duplicate submission keys (duplicate donations) and request keys; amounts that are not whole cents; designations totalling more than the donation; active allocations above the designated amount (reversed ones excluded); and totals that differ from totals the owner states independently (never computed from the batch itself). 7 tests. Nothing is imported by it.

## 4. Onboarding procedure outline (owner-approved, later)
1. Owner supplies the records in an agreed format together with independent totals (opening balances, counts) from the trust's own books. Nothing is invented or estimated.
2. Run the validator on the batch; every problem is fixed at the source, not patched in code.
3. Rehearse on a COPY of the production spreadsheet (a production-equivalent copy does not exist yet): backup, create worksheets, import in the dependency order Causes, Donors, Donations, Donation_Causes, Allocations, Audit_Log, record-count and total reconciliation, the reconciliation page shows no new exceptions, sample donor dashboards match the books.
4. Take a backup copy of the production spreadsheet, repeat the import on production under the write guard, reconcile again, keep the import log.
5. Rollback: restore the backup copy (or the spreadsheet version history) and discard the import log; because Sheets is the only store there is no second system to undo.
6. Only then, with separate sign-off: set `FINANCIAL_ACTIVATION_APPROVED=true`; allocations additionally need the allocation verification gate (`ALLOCATION_SERIALIZATION_VERIFIED=true`).
